# Проект

Это многостраничный фронтенд‑проект IronMebel на `HTML + SCSS + vanilla JS` без сборщика приложений.

Главная цель — production‑готовая, аккуратная и поддерживаемая вёрстка, которая визуально и технически продолжает уже существующий код, а не спорит с ним.

---

## ЧТО: фактический стек и структура репозитория

- HTML‑страницы лежат в корне репозитория: `index.html`, `catalog.html`, `product.html`, `cart.html`, `checkout.html`, `compare.html`, `favorites.html`, `review.html`, `auth.html` и служебные modal/demo страницы.
- Исходные стили лежат в `scss/`.
- Скомпилированные стили лежат в `css/` и **не редактируются вручную**.
- В `scss/` используются:
  - shared partials: `_variables.scss`, `_base.scss`, `_layout.scss`, `_header.scss`, `_footer.scss`, `_components.scss`, `_media.scss`, page partials;
  - page entry-файлы: `page-index.scss`, `page-catalog.scss`, `page-product.scss` и т.д.
- JavaScript лежит в `js/`:
  - `main.js` — общая логика для shared layout и общих компонентов;
  - `layout-include.js` — подтягивает header/footer и общие модалки из `index.html` на внутренние страницы;
  - `catalog.js`, `product.js`, `checkout.js` и т.д. — page-specific логика.
- Статические ассеты лежат в `images/` и `fonts/`.

Если создаётся новая страница, ориентируйся на эту реальную структуру, а не на абстрактный `/src`.

## ЗАЧЕМ: цель дальнейших правок

Все новые изменения должны:

- визуально совпадать с текущим стилем IronMebel;
- сохранять семантику и доступность;
- использовать уже принятые соглашения по структуре, именованию и интерактиву;
- не разносить логику и стили по случайным местам.

Важно: в проекте есть legacy‑фрагменты и недочёты. Их наличие не означает, что их нужно копировать в новом коде.

## КАК: правила для дальнейшей работы

### HTML

- Всегда использовать валидный `HTML5`: `<!doctype html>`, `lang="ru"`, `meta charset`, `meta viewport`.
- Для внутренних страниц придерживаться текущего каркаса:
  - `<div class="page">`
  - `<div data-layout-header></div>`
  - `<main class="im-<page>-page"> ... </main>`
  - `<div data-layout-footer></div>`
- Shared header, footer и общие модалки находятся в `index.html`. Если меняется общий layout, правки нужно вносить прежде всего в `index.html`, shared SCSS и общий JS.
- Один `h1` на страницу. Для хлебных крошек использовать `nav` с `aria-label`.
- Не добавлять новый inline‑CSS и inline‑JS.
- `auth.html` содержит legacy inline‑script и `onclick`; это не паттерн для копирования. Новый интерактив нужно выносить в `js/*.js`.
- Атрибуты держать в понятном порядке: `class`, `id`, `data-*`, `aria-*`, затем остальные.
- Для JS‑хуков использовать `data-*`, а не текст, порядок элементов или случайные селекторы.

### Нейминг и структура блоков

- Основной префикс проекта: `im-`.
- Базовый паттерн для новых страниц и секций:
  - block: `im-catalog-page`
  - element: `im-catalog-page__title`
  - modifier: `im-catalog-page__card--featured`
- Состояния оформляются отдельными классами, как в текущем коде:
  - `.is-open`
  - `.is-active`
  - `.is-collapsed`
  - `.is-added`
  - `.is-filters-open`
- На отдельных legacy‑страницах уже есть другие неймспейсы (`auth__`, `confirm__`, `reg__`). При точечной правке таких страниц сохраняй их существующий namespace и не смешивай его с новым без необходимости.

### SCSS

- Все правки стилей вносить в `scss/`. Файлы в `css/` не редактировать вручную.
- Для новой страницы использовать тот же паттерн:
  - page entry: `scss/page-<name>.scss`
  - page partial: `scss/_<name>.scss` или `scss/_<name>-page.scss`
- Entry-файл страницы должен собираться через `@use`, в духе текущих `page-*.scss`.
- Предпочтительный порядок shared imports:
  - `fonts`
  - `variables`
  - `base`
  - `layout`
  - `animations`
  - `header`
  - `footer`
  - `components`
  - page partial
  - `media`
- Новые общие компоненты выносить в shared partial, а не дублировать по нескольким page partials.
- Текущий проект по факту построен в основном через `desktop-first` / `max-width` media queries, а не через строгий mobile-first. Новые правки должны подстраиваться под существующую архитектуру, если задача не требует отдельного рефакторинга.
- Основные используемые брейкпоинты проекта:
  - `1200px`
  - `1000px`
  - `900px`
  - `768px`
  - `600px`
- Базовые layout‑константы проекта уже заданы:
  - `.page` использует внешний отступ;
  - `.im-container` ограничен по ширине (`1320px`) и центрирован.
- Используй переменные из `scss/_variables.scss` всегда, когда есть подходящий токен:
  - цвета через `--neutral-*`, `--brand-*`, `--blue-*`, `--green-*` и т.д.;
  - типографику через `--font-*-size`, `--font-*-lh`, `--font-*-*-fw`;
  - transition/z-index через существующие переменные.
- Новый токен добавляй в `scss/_variables.scss` только если действительно нет подходящего.
- Предпочитай семантические переменные и существующую шкалу, а не новый хардкод.
- Вложенность SCSS допустима только в текущем стиле проекта:
  - `&__element`
  - `&--modifier`
  - `&.is-state`
  - короткие локальные вложения внутри одного блока
- Не раздувать глубину селекторов и не строить хрупкие цепочки, завязанные на конкретную DOM-структуру без необходимости.

### Визуальный стиль

- Сохранять визуальный язык текущего проекта:
  - светлые нейтральные фоны;
  - акцентный красный brand;
  - тёмный текст;
  - скругления в диапазоне примерно `8px–24px`;
  - плотный, но чистый e-commerce интерфейс.
- Типографика должна опираться на уже подключённые шрифты из `_fonts.scss`, в первую очередь `Inter`, `Exo 2`, `Montserrat`, если контекст не требует иного.
- Не делать “декоративную” вёрстку ради эффекта. Интерфейс должен выглядеть как часть уже существующего продукта.
- Длинные заголовки, названия карточек и текстовые блоки не должны ломать сетку.

### JavaScript

- Использовать обычный браузерный JS без фреймворков и без bundler-specific паттернов.
- Не переводить новые скрипты на `type="module"`, если задача явно этого не требует: текущий проект живёт на обычных `<script src="...">`.
- Общая логика идёт в `js/main.js`, только если она реально нужна нескольким страницам или shared layout.
- Локальная логика страницы должна жить в отдельном page script (`js/catalog.js`, `js/product.js` и т.д.).
- Для внутренних страниц учитывать, что header/footer и часть общего DOM приходят через `layout-include.js`.
- Если логика зависит от вставленного layout, инициализируй её после вставки либо используй page script, который грузится уже после `layout-include.js`.
- Предпочтительный стиль нового JS:
  - `const` / `let` вместо нового `var`;
  - небольшие функции;
  - guard clauses;
  - работа через `data-*` и классы состояния;
  - без лишней глобальности.
- При этом не надо насильно переписывать старые участки только ради стилевой унификации, если задача этого не требует.
- Для модалок, dropdown'ов, табов и фильтров следовать существующему паттерну:
  - переключение `.is-*` классов;
  - обновление `aria-hidden`, `aria-expanded`, `aria-selected`;
  - при необходимости блокировка скролла через `document.body.style.overflow`.
- Для слайдеров сначала проверять, можно ли переиспользовать уже существующий подход на `Keen Slider`, который в проекте уже подключён через CDN.

### Что не считать паттерном

- Наличие inline‑script в `auth.html`.
- Наличие inline‑handler'ов вроде `onclick`.
- Случайные синтаксические/legacy недочёты в отдельных файлах.
- Дублирование логики или стилей, если оно встречается в старом коде.

Если видишь в репозитории спорный legacy-код, это повод быть совместимым с ним, но не повод размножать его дальше.

## Workflow

- Перед правкой стилей определяй, это shared-компонент или page-specific блок.
- Если меняется общий header/footer/catalog/search/shared modal:
  - смотри `index.html`
  - смотри shared partials (`_header.scss`, `_footer.scss`, `_components.scss`)
  - смотри `js/main.js`
- Если меняется только одна страница:
  - правь её `*.html`
  - её page partial
  - её page script при необходимости
- После SCSS-правок использовать:
  - `npm install`
  - `npm run dev:sass` для watch-режима
  - `npm run build:sass` для финальной сборки CSS
- В проекте сейчас нет настроенного lint/test pipeline, поэтому минимальная обязательная проверка после правок:
  - успешная сборка Sass;
  - визуальная проверка затронутой страницы;
  - проверка desktop и основных mobile/tablet брейкпоинтов.

## Итоговый принцип

Пиши новый код так, как будто продолжаешь текущий IronMebel:

- та же структура файлов;
- тот же визуальный язык;
- те же SCSS и JS паттерны;
- меньше абстрактных “идеальных” правил, больше совместимости с реальным кодом репозитория.
- не заливай и не пуш изменения на GitHub если об этом не попросят.

When writing complex features or significant refactors, use an ExecPlan (as described in PLANS.md) from design to implementation.
